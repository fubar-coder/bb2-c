# Proposal

## Why

The website has a Libraries chapter but no reference: a Blitz Basic
programmer cannot look up which commands a library has, which forms they
take and what types their arguments are, and a C developer of libraries
has no browsable API documentation of the library headers and the shared
code. Both exist in the repository, as the token tables of the built
libraries and as Doxygen comments, but nothing turns them into pages.
User decisions of 2026-11-06 (analysis O1):

1. The command reference is generated by an own C tool from the built
   library tables, written as data files under `site/data/` that are
   committed; the build checks in the step that builds each library
   that the committed file equals the generated one. Hugo renders the
   data with a content adapter, one page per library. acidlibs and
   deflibs are included, the RWE userlibs too.
2. The API reference for C developers is Doxygen 1.18 (official image)
   run in the Pages workflow from a committed Doxyfile into
   `site/static/api/` (not committed), served as `/bb2-c/api/`. Scope:
   the library headers, the library sources of acidlibs and userlibs,
   and `shared/`; not `tools/`. The run has no warnings; comment errors
   are fixed in the comments only.
3. Convention: the `@brief` of a library routine that implements a Blitz
   command starts with the command name.
4. Hand-written introductions per library come later; the generated
   pages have a slot for them, and the Libraries overview links the API
   subsite.

## What Changes

- `tools/lib/blitzlib` keeps what it reads but skipped so far: the
  argument types of every form, the result type, the AmigaOS-call
  library, offset and registers, and the object of an object library
  (`!libfin` name and default maximum).
- A new tool `tools/cmdref` (logic in `tools/lib/cmdref`) writes the
  command table of one library file as JSON.
- `blitz_library()` gets an option that runs `cmdref` in the library's
  build step and compares the result with the committed
  `site/data/libraries/GROUP/NAME.json`; acidlibs and deflibs of the
  default variant and every RWE userlib use it. A ctest checks that the
  committed set has no file without a library, each check has a test
  with broken input, and a target copies regenerated files into the
  site.
- The site gets a content adapter and templates under `site/content/docs/libraries/`
  and `site/layouts/` that render one page per library (command
  libraries, AmigaOS libraries, userlibs), with a slot for a hand-written
  description and introduction per library (`site/data/libintros/`).
- A committed `Doxyfile`; the Pages workflow runs Doxygen in
  `ghcr.io/doxygen/doxygen:Release_1_18_0` with warnings as errors before
  Hugo; `site/static/api/` is ignored by git.
- Comments that make Doxygen warn are corrected (comments only; all
  results byte-identical).
- The `@brief` convention is written down in `docs/development.md`.

## Capabilities

### New Capabilities

- `documentation/command-reference`: the command reference of the
  libraries for Blitz Basic programmers - its data, how the build keeps
  it current, and the pages.
- `documentation/api-reference`: the Doxygen API reference for C
  developers - scope, configuration, where it is built and served.

## Impact

- Host tools: `tools/lib/blitzlib`, new `tools/lib/cmdref`,
  `tools/cmdref`, host tests in `tools/tests/`.
- Build: `cmake/BlitzLibrary.cmake`, `libs/acidlibs`, `libs/deflibs`,
  `libs/userlibs/rwe` CMake files, `libs/CMakeLists.txt` (tests).
- Site: `site/data/libraries/` (generated, committed),
  `site/content/docs/libraries/`, `site/layouts/`, `site/README.md`,
  `.github/workflows/pages.yml`, `.gitignore`.
- Comments in `libs/` and `shared/`; `docs/development.md`, `TODO.md`.
- No program, library file or compiled executable changes.
