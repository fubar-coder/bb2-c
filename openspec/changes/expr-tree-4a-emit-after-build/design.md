# Design

## Context

The series and its check: `expr-tree-1-typing/design.md`. Enter/exit actions: `expr-tree-3c-calls/design.md`; the lookup without use: `expr-tree-3d-library-calls/design.md`; the side-effect table: `docs/blitz2/expression-tree.md` (written by changes 3a-3e).

## Goals / Non-Goals

**Goals:** emission after the build with today's bytes; no code patched, rewound or moved inside an expression.

**Non-Goals:** typing changes; `countpees`, look-aheads, assignment copies (change 9).

## Decisions

### 1. The unit: a top-level `maineval2`

A call of `maineval2` from a statement builds and emits one tree; a `maineval2` reached while building (a parameter, an index, a bracket) adds a subtree. The arena is marked at the top-level entry and released after its emission; reset per statement as before.

### 2. Flow typing and errors at build time

The type so far and every type error are computed while the tree is built, in reading order (step 1's function); emission raises only the errors that today come from emission itself (none known; task 1.2 checks). This keeps "the first of two errors" (spec).

### 3. Constant fold on nodes, value by emit-and-run

A fold is decided when an operator's two operands are constant nodes (today's pairwise rule). The value is still obtained by emitting the operation into the buffer and running it (`callregs`), so FFP and Quick values and the linked libraries are today's; `lasta6` is restored; `fraclitdrop` (#1186) and the relocation cleanup (#1049) stay; no fold while `nomemleft`. Alternative (computing on the host side in C): other values possible for FFP; not byte-identical; a named step 6 item at most.

### 4. The dropped conversion keeps its library

`cmpownleft` rewinds a conversion `varcont` emitted for a one-element left operand of a comparison, frees its relocations and restores `lasta6`, but a library the conversion's routine linked stays linked. In the tree the conversion is not emitted at all; the node carries "dropped conversion via routine R" and its enter action makes the use of R's library (`uselib3`) without code. A test source whose only use of that library is such a conversion pins it (task 1.1).

### 5. Arena blocks

Further blocks of 4 KB by `AllocMem` when the static block is full, freed at the statement reset. The size per node and the worst case are measured (task 2.5). Failure: the error of open question 1, without retry.

## Risks / Trade-offs

- [A side effect at the wrong action] -> bytes differ in the check; the side-effect table names where each belongs.
- [Memory: up to about 128 KB for a line that fills the 8 KB macro buffer (analysis estimate)] -> blocks are freed per statement; measured in 2.5.
- [Compile time] -> measured (`corpus_cd` duration before and after), reported; no budget exists for the compiler's speed.

## Planning choices (mine, not the user's)

- Decision 3: `Point: fold by emit-and-run on nodes — L1 Unlikely / I2 Medium / E2 Reasoned → Monitor`.
- Decision 4: `Point: a library linked only by a dropped conversion goes missing — L2 Possible / I2 Medium / E2 Reasoned → Plan` (the coordinator's recorded Plan choice; task 1.1 is its test).
- Arena error: rated `L1 Unlikely / I3 Observable / E2 Reasoned`, but D-018 (out-of-memory fixes) bears on it as an answer for another case: Decide (proposal, open question 1).

## Findings (implementation)

- Task 1.1's source was built by hand: `r.f = (q = 2)` with `q` a Quick. The Float that `r` wants makes `varcont` convert `q` with floatquicklib's routine (`qtof2`, `qutofl`, whose call loads ffplib's base: ffplib is first used there too); the comparison drops the conversion (`cmpownleft`, a Quick to Float), and the comparison's Word is converted to the Float by ffplib (`wordtofloat`), so floatquicklib is linked by the dropped conversion alone. Checked on main with AB3 mode's command line compiler (`blitz2-ab3 -s`): the program is 148 bytes longer than the same program with `r.f = -1`, and adding a conversion `f.f = q` to both makes them 16 bytes apart (its code only). The test is `tests/blitz2/expr-build.test.bas` (case `dropconv`, with and without runtime error checking, `blitz2_expr_build_prev`), with the fold cases of task 1.3.
- Task 1.2: `tests/blitz2/expr-errors.test.bas` and its data sources (`expr-errors.test/`): the spec's `a$*2+nofunc{}` is "Type Mismatch" on main (the `2` under the type so far String, `consttype2`, before the operator), so the operator's error is `a$*a$` ("Illegal Operator for Type", raised by `doop` when the operator is emitted, before the next element is read); a missing bracket after both, an error in the first parameter of a Function and of a library function before an unknown Function after it, a String for a Word parameter ("Can't Convert Types", at the end of the parameter) and a division of two constants by zero before an unknown Function ("Division by Zero", raised by the fold's check when the operator is emitted).
- Task 1.3's fold while the object buffer is full: `tests/blitz2/expr-fold-full.test.bas`, after the pattern of `compiler-fold-buffer-full` (#1190): a child compiled with an object buffer of 2992 bytes, which 280 folds fill before the folds of a Mod (modlib's first use), a sum after a variable, a negated bracket, a Float and a Quick product and `Not` of a sum with a division.
- Decision 1 as built (task 2.1): the unit is a `maineval2` outside an expression (`exprtree_begin`); each part of the code is an action (`struct expract`: the function, its node, two arguments, the `regat`, `varmode` and `evaldepth` of the place it was read) appended to the unit's list in reading order, which is the post-order walk of the tree with each node's enter actions before its children and its exit actions after them; the owner runs the list when the expression is built (`exprtree_run`) and frees the unit's nodes (`exprtree_unwind`). Shared code that statements call too (`pushap`, `handlevara`, `sendtype`, `baseadd`, `highadd`, `stepemit`, `libparams`' `stackuse`, `getmaxel`'s scaling, AmiBlitz3's defaults and argument depth) records its code through `emitact`/`stateact`, which run it at once outside an expression. Every emitter state the build used to read from the code it had written is now a record of the build (`bforth`: the forthstack's `constgot` and `wordval`; `bconv`, `blit`: cmpownleft's conditions by the order of the recorded actions; `bsbase`: `sbasegot`; the intrinsic's state for `libjsrcode`); the emitter's forthstack keeps only the positions the fold runs from. A constant computed in the middle of an expression (`evalconst2`: a `~` constant, found by `compiler-cmake-tilde-in-string`) is a unit of its own with the expression set aside (`exprsuspend`, `exprresume`).
- Library use at build time (answered 2026-11-24, rounds/tree/decisions.md "expr-tree-4a findings: libraries at build, divzerobuild"): a library's first use gives it its variable offset from `varoff`, which the variables an expression makes at first sight share, and copies it into the library area in the order of first use; used at emit time, a library used by the code of an element before a new variable would get its offset after the variable's (`a$="x"+n$` with a new `n$`, `workstart`). So every library is used while the expression is built, at the moment the original used it: the uses of a part of the code where that part is recorded (`tokuse`, `userjsruse`: what `tokejsr` and `userjsr` use, with the libraries of the register lists, the blitz mode flag and its check routines, and the mode errors in their order; `convprep`, `opprep`: the routines of a conversion and an operator's handler), a function's at its lookup (`calluse`, as since 3d). The library's relocations must keep their place in the program's relocation list (written in list order to the executable): `uselib3` keeps them while the expression is built (`reloccapture` in `addoff2`) and moves them into the list at the library's first `uselib3` while the code is written (`relocsplice`; for a lookup's use an action at the lookup's place), which is where the original added them; those of a library whose calling code is never written are freed at the unit's end, as `cmpownleft` freed them. Decision 4 (the dropped conversion keeps its library) follows from it: the conversion's library is used when the conversion is recorded.
- Decision 2 (errors at build): the errors the original raised in its code are raised where the code is recorded, in the same order ("Can't Convert Types", "Illegal Operator for Type", "Type Mismatch", the blitz/amiga mode errors). "Division by Zero" of two constants needs the divisor's value, which only the code gives: `divzerobuild` runs the operands' actions and the operation up to `divzerochk` behind `pc` while the expression is built and sets back what they changed; the code is written again later and the check finds the same divisor (task 1.2's `div0name.bas` came out "Procedure not found" without it). The fold itself still runs when the code is written (decision 3).
- Checks kept in the code (`interr2`, not reached): no code is written while an expression is built (`pc` unchanged), no library is used for the first time while the code is written (`uselib3`), the type an operator's code computes is the one the build decided (`binopact`), and `cmpownleft`'s conditions hold where the build decided the drop (not checked in a pass whose code is not stored).
- Decision 3 as built (task 2.2): the fold is decided on the nodes while the expression is built: the build's record of the pending elements (`bforth`: whether each is a constant, today's pairwise rule) gives the operator `BNF_FOLD`; what `nocando` made no constant (`^`, a Long or Float `Mod`, a raw Quick's `*` and `/`) is `BNF_NOFOLD`. The value is still computed by running the code when it is written (`constfold`, with `fraclitdrop`, #1049's relocation cleanup and `lasta6` as before, no fold while `nomemleft`); where it runs from, the relocations and `lasta6` of that place are kept by the left operand's first action (`startmark`), which every operand has, so the emitter's `forthstack` (`struct forthent`, `forthsp`, the element's push and the expression's pop) is gone, with `nocando`. The left operand's start is the original's `forthsp[-2].pc`: an operand begins with its first element, a bracket, a minus sign or `Not` write no code before it, and a left operand is never in d7 (no spill before it). The action between a comparison's operands (`midact`: #978's facts, `cmpownleft`) is recorded for comparisons only, the other operators read nothing it records.
- Task 2.3 as built: #978's facts are the operands' while the expression is built: an operand is one byte value when the action of the value whose code ends in the ext.w is the last one that writes code in it (`bbyte`), one integer constant from 128 to 255 when the constant's action is its only one that writes code (`bcst`, with the leaf: its value as its code holds it); `exprtree_left` marks the walk's leaf (`EXF_BYTEVAL`, `EXF_BYTECONST`, `right` the constant's leaf), `binopbuild` hands the facts of both operands to `exprtype_binop` and marks the constant `ELF_SIGNEXT`, whose code (`constemit`) is the sign-extended byte; `isbyteconst`, `byteconstext`, `bytevalend` and the facts of `midact` are gone, `iswordconst` and `constval` with them (the build has the Word value of a constant: `constword`). A RESULT carries only `EXF_CMP` of its left operand's flags.
- Task 2.4 as built: `cmpownleft` and `fraclitfloat` are gone. `ownleft` marks the dropped conversion's leaf (`ELF_DROP`: `contcode` writes no conversion) and frees the reloc entries its routine's first uses left (`relocforget`: they are exactly the relocations `cmpownleft` freed with the rewound code; a later call of the same library adds none, as in the original); the libraries stay used (decision 4, task 1.1's `dropconv`). A literal made a whole number that is the left operand is written as its FFP value with the sign bit flipped once per minus sign after it (`ELF_FFP`; the runs of minus signs are chained in `blit` and write nothing, `EXF_ABSORBED`), as `fraclitfloat` rewrote it; `litat`, `litend`, `litffp`, `litint`, `fraclitdrop` and `conv`'s `at`, `off` and `a6` are gone (`conv` stays for `arrevalchk`'s narrowing). `compiler-quick-compare` and `compiler-byte-const-compare` pass (FIXED), `compiler-compare-compound-left` fails as on main (REPRODUCED).
- Task 2.5's figures (a throw-away build of `blitz2-ab3` that printed the arena's high water per statement, not committed): a node is 46 bytes, an action 24 bytes on the 68000; a usual line (`b.l = a(x+1)*3+f{x,y*2}-Abs(q*4)+Len(s$+"cd")`) 4940 bytes, in the static block (7728); 63 parentheses 9144 bytes (1 further block), the #1080 case (63 parentheses, 31 calls, 28 `Right$`) 25768 bytes (5 blocks); a sum of 100 terms `kk+kk+...` 28086 bytes, of 1000 terms 280812 bytes (67 blocks), a line of 8 KB from macros (2700 terms) 758222 bytes (184 blocks): about 280 bytes per term of a chain (the leaf of the walk, the variable's node, the operator and its result, and the actions of the operand's start and end marks, the value's code and the operation). That is far above the design's estimate of 128 KB for such a line; a line of 8 KB needs about 760 KB of free memory now (with less: "Out of Memory"). Possible reductions, not made: the operator node as its own result, the marks of an operand only where a fold or a comparison reads them. The failure path: the host test `blitz2_exprtree` ("further blocks beyond the static one, Out of Memory without them": a stub refuses the second block; `exprtree_nomem` once, no retry, the blocks given back by the reset), also with `-DHOST_SANITIZE=ON`; an emulator case with too little memory was not made (the machine's memory is the emulator configuration's; a test would have to fill it first).
- Task 2.6 (stkrun, `blitz2-ab3` with a 200000-byte stack, compile only, the programs run under `reqtrap`; main = 7ec3512e2 against this change's last commit): 63 parentheses (q63) 15363 -> 16731, the #1080 case (x1) 22183 -> 24667, 63 times `-(` 21159 -> 22527, 16 `Right$` (n16) 9499 -> 10631, `chr_mem.ab3` 2959 -> 3251, 31 nested Functions (g31) 13407 -> 14631, 30 nested arrays (h30) 12991 -> 14087, 32 nested `Abs` ("Expression too Complex", x3) 15679 -> 17579, a chain of 100 and of 1000 terms both 1719 (main 1611: flat), 200 minus signs 1719 (1611). Against main before step 2 (60d25326f, the figures of `expr-tree-2-operators`): 63 parentheses 15619 -> 16731 (+7.1 %), the #1080 case 22811 -> 24667 (+8.1 %), 63 times `-(` 22927 -> 22527, 16 `Right$` 9851 -> 10631 (+7.9 %), `chr_mem.ab3` 3071 -> 3251 (+5.9 %), the chain 1623 -> 1719 (flat): within +10 %. The growth over main is the build's frames (the walk keeps its result's facts, `binopbuild`'s and the actions' locals); 32 nested `Abs` has no figure from before step 2 (+12 % over main).
- `blitz2` 115804 -> 122848 bytes, `blitz2-ab3` 154692 -> 161824 (main against this change's last commit). Compile time: the check's durations under parallel load (`ctest -j8`) are noisy: `corpus_cd` 58 s with the arena's commit, 94 s with the last one, `corpus_cd_ab3` 67 s and 65 s; no budget exists for the compiler's speed.
