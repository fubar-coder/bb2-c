# Design

## Context

After `expr-tree-4b-lookaheads` the expression is a tree before emission (flow typing at build time, `expr-tree-4a-emit-after-build`); step 1's function decides each operation from (operator, left, right, facts). Variant C of #1178 and its rounding ("Zwischenlösung: / gegen Null (Recommended)") are the value rules of a mixed operation. The series: `openspec/changes/archive/2026-11-24-expr-tree-1-typing/design.md`.

## Goals / Non-Goals

**Goals:** typing by operands; the changed results listed exactly by the model before the implementation.

**Non-Goals:** step 6 optimisations.

## Decisions

### 1. Typing pass after the build, errors still at build time

The flow typing at build time stays for the errors (the first of two errors, spec `compiler/expression-limits`); a second pass over the finished tree (iterative along chains) computes the operand types and the conversions; emission uses them. Where operand typing would make a source that compiled refuse (or the other way), that is a named change of its own (task 2.2 lists such cases: decision 10).

### 2. The model first

The expression matrix's model (`tools/lib/exprmatrix/model.c`) has the decided rule as a rule set (`EM_RULES_DECIDED`, decision 7); the cells whose value changes are the named cells (`tests/corpus/tests-exprmatrix/named-cells.tsv`). The 376 places of #1178 are re-run with the same rule. The implementation is done when the compiler gives the model's values for every cell.

### 3. Readable tables of today's rules first, generated and checked

Decision (user, 2026-11-24, `~/.local/share/bb2-c-work/decisions/rounds/tree/decisions.md`, "expr-tree-5: readable tables of today's type rules first"). Suggestion: "Wäre es nicht sinnvoll die bestehenden Typ-Konvertierungsregeln, bzw. Operator-Ergebnis-Typen zu ermitteln und dokumentieren - unter Einbeziehung des Ziel-Datentyps, falls notwendig?"; answer to "als neue erste Aufgabe einplanen?": "Ja, mach das."

- **Tool**: logic in `tools/lib/exprtype_tables/`, command in `tools/`, host tests in `tools/tests/` (CLAUDE.md rule 6); `programs/blitz2/src/exprtype.c` is linked in, as `programs/blitz2/tests/host/test_exprtype.cpp` does. It is used again by Q4 (below) and by the last group.
- **How the wanted type enters** (confirmed by task 1.1 in `exprtype.c` and its callers in `eval.c`): no function of `exprtype.c` sees the wanted type itself; it is only the initial value of the one type so far of the expression (`*e->type`: the destination, parameter or field type, Long for an array index, 0 for `If`/`While`/`Until`/`Print`; 0 again for the right operand of a comparison, `exprtree_enter`). Each element is decided by `exprtype_element(tsf, own, facts)` at the type so far before it (`contleaf`: `l->tbefore`), which converts it up, promotes the type so far to its own type, or holds a Quick under a Long raw (#1178). Before the right operand is read, `exprtype_leftop(op, tsf, lraw)` (`exprtree_pre`) turns a raw left operand of a comparison into a Quick and allows `ownleft`; the right operand then starts at the type so far after the left one (`n->tbefore`). `exprtype_binop(op, left, right, facts)` (`binopbuild`, `operate`) takes left = that type so far and right = the type so far after the right operand, converts the left operand to `right` (or, under #1182 and in a comparison, the lower one up), computes with the handler of that type and returns the new type so far. So the wanted type reaches an operator only through the type so far its left operand was met at, and a later operator of a chain sees the type so far of the chain instead: the result depends on the position in the chain, i.e. on the operand order. The tables make that visible: the key of a row is (operator, left type, right type, wanted type), and a chain position is a column group: the wanted type column shows the type so far at which the operand is met (the left operand of a chain starts at the wanted type, a later operand at what the chain gave so far). A note per group shows the same operator with swapped operands (`a+q*4` against `q*4+a`) and marks the rows where the two differ; that list is the order dependence the change removes.
- **Tables**: one per operator group (arithmetic `+ - * /`, bit operators `& | AND OR EOR`, shifts, `Mod`, power `^`, comparisons, the bit test/set operators), each cell giving the result type and the conversion of each operand (from -> to, a raw Quick cut). Exceptions are notes under the table with their issue: #1178 raw Quick, #1182 comparisons, #1188 constants with a fraction under Byte, #1209 bit operators under Quick, #978 sign-extended constants, #1179 Word operands of a later index. Constants and elements (`exprtype_element`, consttype2) are a table of their own: wanted type x constant facts -> type.
- **Where**: a generated page `docs/blitz2/expression-type-tables.md`, linked from `docs/blitz2/expression-types.md`, not an appendix of it. Why: the page is written entirely by the tool, so the check is a whole-file comparison without markers inside hand-written text, and the hand-written page keeps its explanations and measured examples.
- **Check**: in the build step that produces the page (a custom command/target of the docs, CLAUDE.md "Code conventions": a failed check means the result is not built, no stamp files); a test with deliberately broken input (a changed cell, a missing note) must fail it.
- **Findings of task 1.1**: the tool (`tools/lib/exprtype_tables`) has a rule-set interface (`struct ett_rules`: a cell of (operator, type so far, left, right, facts), an element, a constant); today's rules are the flow through exprtype.c's functions, given as primitives that are either exprtype.c or the rows of `exprtype.tsv` (the test compares every cell the page shows from both, and the page from both). The cells cover two variables or function values per operation; a constant operand is the row of the type the constants table gives it. Three exceptions are not decisions of `exprtype.c`, so their notes are fixed text beside the generated cells: #1209 (the whole part of a Quick under `&`, `|`, `AND`, `OR`, `EOR` is `quickwhole` in `eval.c`; the cells show the Quick operation), #1183 (a compound left operand of a comparison is not one element) and the use of #1179's mark (only the Long handlers of `*` and `/` compute two Word values inline; `exprtype_binop` marks every plain operation). `exprtype.tsv` records the facts of #978 only for two Word operands, so the page shows #978 for a Byte value under a Word type so far. Today's page: arithmetic 4 tables (`+`, `-`, `*`, `/`), bit operators 1, shifts 1, `Mod` 1, `^` 1, comparisons 1, bit test and set 2, each 25 rows of 6 columns; order-dependent cells: 6 each in `+`, `*` and the bit operators (a Long and a Quick under none, a Byte or a Word type so far: `l+q` is a rounded Long, `q+l` a Quick), 4 in the comparisons (a Byte or Word and a Quick under a Long type so far: the whole number is converted to Long on the left, to Quick on the right).
- **Q4**: each candidate rule (open question 1, including "constants as integral or fractional numbers") is printed by the same tool as the same tables beside today's, the cells that change and the CD places marked, in the decision report. After the decision the page is regenerated with the chosen rule in the implementation group; the changed cells are the named ones.

### 4. #1183 is a case of the operand typing

Decision (user, 2026-11-24, `~/.local/share/bb2-c-work/decisions/rounds/tree/decisions.md`, "#1183 folded into step 5"): "Fold #1183 into step 5 (Recommended)". Rule: `compare-compound-left` is merged into this change; its test, spec scenarios and the value cases of its count are inputs of this change; the recorded order "#1180 steps 1-4, #1183, step 5" becomes "steps 1-4, step 5 with #1183". Why: the count (`cmp-compound-1-1/report.md`, finding 1) showed that after step 4 the typing is still in reading order (the left operand's conversions, raw-Quick handling and library use are recorded before the comparison operator is read), so a left operand typed by its own operands needs a lookahead, a re-read or bottom-up typing, which is this change's typing pass. The comparison node hands no wanted type to its left subtree (as to the right subtree since #1177); the pass types the left subtree by its own operands, and `compareop`/`cmplq` compare the two operand types exactly. The one-element node rule of #1177 is the special case.

The cases of the count (proposal, open question 1) are inputs of the decision round Q4: each candidate rule shows their values. Findings the round must face: a rule that types a Word sum in its own type changes `r.l=(w+v>c)` when the sum wraps, and a Quick product overflows where the Long context was exact (`q*1000`); the earlier requirement that a comparison with a whole-number compound left operand keeps its result therefore does not go into the spec before Q4. The scope (every compound left operand, or only where a Quick or Float is inside or a Long constant meets a Float context) is part of open question 1; the premise of the old plan, that (b) changes fewer executables, is false on the CD (both change none).

### 9. The 48.16 format and its routines

A 48.16 value is a register pair: D0 the low 32 bits (a 16.16 value), D1 the high 32 bits ("C7: the wanted type sets the intermediate format", remark: "16.16 in D0 und den oberen 32 Bit in D1 (oder umgekehrt) ... wenn die oberen 32 Bit 0 sind, dann haben wir einen Optimierungsansatz"), with a fast path when the high part is the sign extension of the low part, decided at compile time where the tree knows the operand formats. The routines are the port's own in `libs/compilerlib` (system library 64030, linked in every library set), no libgcc and no libnix (decision "cost and the wide division"); the division is an own routine faster than the prototype's 5912 cycles, aim below libgcc's 3566, measured on the A500 (`tests/perf`). Division and `Mod` follow parts 3 and 4; a 48.16 division by 0 gives the largest value with the dividend's sign, as `lqdiv` ($7FFFFFFF or -$7FFFFFFF as the whole part; user, 2026-11-25, "expr-tree-5 after 2.2: 2.0 under bit operators, division and Mod by 0": "Größter Wert mit Vorzeichen (Recommended)"), under every wanted type; in the format of the wanted type (decision 6: a Quick $7FFFFFFF as today). The cycles of P+ are accepted; the slower forms are made faster where possible, also by tree optimizations (#1180 step 6 candidates).

Task 3.5 (the routines, `libs/compilerlib/compilerlib.c`, `$D603`-`$D60E`): `q48add`, `q48sub`, `q48mul`, `q48div` with one entry per value of a division by 0 (`q48div` a Long or none, `q48divq` a Quick, `q48divw` a Word, `q48divb` a Byte; error check `q48divchk`), `q48mod`, and the casts `l2q48` (Long), `q2q48` (Quick), `q48floor`, `q48trunc` (to a Long; a Word or Byte is the Long's low word, `ext.l`; 48.16 to 16.16 is D0 itself). Registers: a in D0/D1, b in D2/D3, the result in D0/D1; D2/D3 changed by the two-operand routines, every other register kept (no pending register needs a save for D4-D7 and A0-A6). The emulator test (`libs/tests/libtest_q48.c`, in `libtest compilerlib`) compares every result with `exprarith.c` compiled for the m68k (5309 pairs: edges, the rare steps of the digit loop, random). The division: the divisor's low zero words dropped with as many dividend words (the same quotient), then one DIVU per digit for a divisor below $10000, Knuth's algorithm D with two divisor digits below 2^32 (the exact test with the low digit, so no add-back), bit by bit beyond (at most 48 steps). Cycles on the A500 (`tests/perf` `bcompilerlib`, the routine with JSR and RTS, the loads subtracted): 1.5/2.5 1741 (libgcc 3566, the prototype 5912, both without the call), 100000.5/2.5 2041 (libgcc 3835), 100000.5/100000 1801 (libgcc 3712), 1.5/3.0 1045, 100000.5/100000.5 3183; `q48mul` 492 (two 16.16 values), 372 (a factor without a fraction), 905 and 1316 (one or both wide); `q48add` 54; `q48mod` (7.5 Mod 2.0) 1400. Finding: a program gets a library whole, so every program that uses mixmult, qqmult or lqdiv (#1178) now carries the 48.16 routines too (compilerlib 354 to 1202 bytes in a program; the prev run: 9 CD sources in each mode and the test programs with a Quick under a Long, 848 to 860 bytes larger, outputs unchanged).

### 11. Group 3: the shared C and four rule points of P+

### 12. Task 3.6: the constant fold in C

### 14. Task 4.3: the speed of the slower forms

The rule of the task (user, 2026-11-26, `rounds/tree/decisions.md`, "expr-tree-5 4.3: \"byte-identical\" means the outputs"): every program gives 4.2's values and outputs; the changed executables are an intended change. Only the code of 48.16 operations and of 48.16 Selects changes (`eval.c`, the typing pass's emission; `exprtyping.c` and the libraries are unchanged). The benchmark `tests/perf/bench/bq48.bas` measures the compiled forms (the routines included); `tests/blitz2/expr-q48-paths.test.bas` checks the values of every changed path against 4.2's.

- **The operands by register moves** (`p5callin`, `p5moves`): the operands go to d0-d3 by moves in parallel (a cycle by `exg`) instead of through the stack.
- **`+`, `-` and the comparisons inline**: compilerlib's add/addx and sub/subx in d0-d3 instead of the jsr to `q48add`, `q48sub` (the 4.1 implementer's point "q48add/q48sub are called rather than inlined").
- **A constant Case of a 48.16 Select** (the user's candidate of 2026-11-26) is `cmpi.l`/`tst.l` against the value on the stack, the Case's load (`moveq`, `move.w #` of a Byte or Word, `move.l #` without a relocation) taken back. The syntax tree of #1180 does not make it moot: the comparison is the Select statement's code (`docase`), which the tree of an expression does not change; with a tree the Case would only be known as a constant before its code is written.
- **A 48.16 root under `ETC_FLOOR` by the routines of #1178** (`p5mixfloor`): `+`, `-`, `*` of a whole number (a Word or Long value, a whole constant) and a 16.16 value (`+` and `-` also of two 16.16 values) is `mixedop` (l + floor(q), l - ceil(q), mixmult): the operands have at most 32 bits, so the 48.16 operation is exact and its whole part rounded down is the routine's. Not for `/` (`lqdiv`'s and `longdiv`'s division by 0 and range differ from `q48div`'s) nor for the product of two 16.16 values (`q48mul` cuts towards zero at 1/65536 before the floor, `qqmult` rounds the exact product down: `-0.5 * (1/65536)` gives 0 and -1).
- **The low 32 bits under `ETC_KEEP`** (`p5lowmark`, path `P5Y_LOW`): under a wanted Quick, a root chain of `+` and `-` of whole numbers and 16.16 values computes in 32 bits (a whole number as l << 16 modulo 2^32), a root `*` of a whole number and a 16.16 value as l * q modulo 2^32 with three MULU (D(r+2), D(r+3), only below d6; else the 48.16 code).

- **The fast paths** (the user's decisions of 2026-11-26, "fast path for a Quick with a constant divisor/factor", "the Word fast path q*w", "a whole Quick divisor at run time"; `p5fastmark`, `p5fast`, `p5wholediv`): a 48.16 `/` of a 16.16 value by a whole constant 2 <= |d| <= 65535 (two DIVU) and a `*` of a 16.16 value and a constant below 1 (two MULU) give a 16.16 result in one register; a 16.16 value times a Word, a Byte or a whole constant of the Word range is the exact 32 x 16 product as a pair (two MULU); a 48.16 `/` by a 16.16 value tests it at run time and divides by a whole part with four DIVU over the dividend's 64 bits, a fraction or 0 calls `q48div`. - [The rule is chosen without seeing the CD impact] -> the 376-place run and a CD count are shown with question 1.
