# Proposal

## Why

The goal of #1180: the type of an operation depends on the wanted type and on both operands, not on their order. User, 2026-11-21 ("#1178 direction: variant C; expression tree planned"): "Und ja, base+q*4 muss das gleiche ergeben wie q*4+base, aber das machen wir in einem späteren Schritt". Requirement handed from #1178 (2026-11-22, "#1178 Q1"): "Zu #1178: Wichtig ist nur, dass nach dem Expression Tree dort 4.5 rauskommt" (`NPrint 1+1+1+q` with `q=1.5`; 4 until this change). After changes 1-9 the whole expression is a tree before emission; this change replaces the flow typing by operand typing. It is the named change of results of the series.

It also fixes #1183 (bug-orig, compiler, wrong-result; severity proposed 1): since #1177 a comparison compares a one-element left operand with its own value, but a compound left operand (`q*2`, `q+q`), a negated one (`-q`) and a Long constant on the left under a Float context are still evaluated in the type the expression is wanted in, so a Quick inside is cut and the boolean is wrong (`r.l=(q*2>2.5)` with `q=1.5`: 0, expected -1). The change `compare-compound-left` planned that fix on its own; its count (`~/.local/share/bb2-c-work/cmp-compound-1-1/report.md`) showed that the left operand's types are still decided in reading order, before the comparison operator is read, so the fix needs bottom-up typing, which is this change. User decision, 2026-11-24 (`rounds/tree/decisions.md`, "#1183 folded into step 5"): "Fold #1183 into step 5 (Recommended)"; the recorded order "#1180 steps 1-4, #1183, step 5" (`rounds/quick`, 2026-11-22) becomes "steps 1-4, step 5 with #1183". `compare-compound-left` is archived unimplemented (`openspec/changes/archive/2026-11-24-compare-compound-left`).

## What Changes

- **Readable tables of today's type rules first** (user, 2026-11-24): a C tool derives from `exprtype.c` tables per operator group (operator, left type, right type, wanted type -> result type and conversions, the exceptions as notes with their issues, constants and elements in their own table); they go into the docs with a build check that they equal the tool's output. The decision round showed each candidate rule as the same tables beside today's.
- **Operand typing by the decided rule P+** (below): a typing pass over the built tree; bottom-up each node gets the type and format its operands give (operator, left type, right type), top-down the wanted type; neither depends on the order of the operands of `+`, `*`, `AND`, `OR`, `EOR`, the comparisons, nor on the place of a subexpression in a chain.
- **The left operand of a comparison is typed by its own operands**, whatever its shape (compound, negated, a Long constant under a Float context), as the right operand since #1177 (scope (a): every left operand); `-q` already has its raw value (`quick-long-arithmetic`, design decision 7) and stays a scenario as a guard.
- **48.16 intermediates** where a Long is wanted or takes part: a register pair (D0 the low 32 bits, a 16.16 value; D1 the high 32 bits) with a fast path decided at compile time, its arithmetic in an own 68k routine set (an own, faster 48.16 division, aim below libgcc's 3566 cycles); no libgcc or libnix in the libraries.
- **Shared C for the compiler**: `exprtyping.c` (the typing pass as a pure function) and `exprarith.c` (whole, 16.16 and 48.16 arithmetic on `int64_t`, bit-exact with the 68k routines: `qmul`, `qdivide` with its last bit, division by zero, `domodlong`), compiled by blitz2 and the host tests; constant folding of whole, Quick and 48.16 operations in C with `exprarith.c` instead of running the emitted code (byte-identical; Float folding stays as today). The matrix model stays an independent implementation, the oracle of both.
- The bug-fix workflow for the order dependence: one new bug-orig issue, #N (new), "the value depends on the order of the operands", with the table of changed cases (user, 2026-11-24, "expr-tree-5 Q4 batch 1", F4: "Ein neues bug-orig-Issue (Recommended)"); the issue is created by the coordinator. One fix commit with `Fixes #N` and `Fixes #1183`; tests `compiler-expr-N-*`; one fix-overview row; #1180 stays the enhancement issue.
- The bug-fix workflow for #1183 (rule 4, spec `testing/bug-fix-workflow`): the BASIC model test `tests/bug-orig/compiler/compiler-compare-compound-left.test.bas/.toml` gets `fixed-orig = 1183` and the originals' values as `compiler=orig195` deviations (no `.expect`/`.orig`); the #1183 part of #1177's kind-F row in `docs/blitz2/deviations.md` becomes its own entry; `BUG(orig) (#1183)` (marker at `ownleft`, `eval.c`) becomes `Fixed (#1183)`; `Fixes #1183`.

## The decided rule P+

Decided by the user on 2026-11-24 (`~/.local/share/bb2-c-work/decisions/rounds/tree/decisions.md`, from "Q*W and Q*L with a 32.16 result" to "expr-tree-5: shared C for typing, arithmetic and folding; task 2.2"; the analysis `~/.local/share/bb2-c-work/expr-tree-5-analysis/report.md`, section 1): "C7-Familie (Recommended)", C7K-long's skeleton ("C7K-long as working assumption") with the analysis's changes 1-8 and the answers F1-F7 ("expr-tree-5 Q4 (P+ round 1)", "(P+ round 2)"): "Result: the rule is P+ (changes 1-8 of the analysis) with these answers." The parts, each with its source, are design decision 6.

- **AB3 mode**: the same rule ("expr-tree-5 Q4 batch 1", F3: "Gleiche Regel auch in AB3 (Recommended)"); the port then differs from AmiBlitz3 there (`docs/ab3/variant.md` entry; affected oracle tests marked, counted in task 4.2).
- **Cost**: the measured cycles are accepted, the slower forms are still made faster, also by tree optimizations ("expr-tree-5 Q4: cost and the wide division": "Option 1: \"Ja, gemessene Zyklen akzeptieren\", aber bei der Umsetzung bitte trotzdem versuchen die Geschwindigkeit zu optimieren. Ggf. indirekt auch über Expression Tree-Optimierungen?").
- **The wide division**: "Eigene Routine, schneller (Recommended)": an own 68k routine, no libgcc/libnix. Finding of task 2.1 (`expr-tree-5-rules.md`, "libgcc's 64-bit arithmetic"): libgcc's `__muldi3`/`__divdi3` do not link in a Blitz library by themselves, they call `__mulsi3`, `__udivsi3` and `__umodsi3`, which this toolchain has in libnix13 and libc, not in libgcc; no library of the port links any libgcc routine today (`blitzhelp.h`: "no libgcc in libraries").

## Not in scope

Optimisations the tree allows beyond the ones named in the tasks (#1180 step 6: folding beyond pairs, immediates, register saves; `x/2*2` as an even-number operation, TODO.md); the comparison of strings and the boolean's type in the context (#1177's rule, unchanged); index typing (#1179); string operations.
