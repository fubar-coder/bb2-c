## Context

The audit (`~/.local/share/bb2-c-work/analyse-ndk-a345.md`, 2026-11-14,
main `c2825774`) lists the 35 NDK functions with an a3 parameter (5 also
a4), the seven NDK macro calls in the libraries, the hand-written calls,
and a prototype of the wrapper and the poison
(`~/.local/share/bb2-c-work/ndk-a345/proto/`). The decisions of the user
(2026-11-14) are in the proposal; this design records how they are built.
Issues: #516, #1027 (EZRequest), #328 (fixed in round RP), #1028 (fixed,
no deviation entry yet).

## Goals / Non-Goals

**Goals:** a library that calls an affected function raw does not
compile; the used affected functions keep a3/a4; an NDK update cannot add
an unprotected function unnoticed; the dead varargs wrappers go.

**Non-Goals:** the hand-written `__asm` calls, a disassembly scan, calls
from Blitz source, blitz2/TED (proposal "Out of scope").

## Decisions

### D1 Shadow headers, generated by CMake
`proto/X.h` includes `<inline/X.h>`, so a header `inline/X.h` found first
in the include path gets control around the NDK's definitions, independent
of the include order in the library source, and the sources keep the NDK
names. There is one shadow header for every NDK inline header the
libraries include (the audit names asl, cia, commodities, console,
datatypes, dos, exec, gadtools, graphics, icon, intuition, layers,
mathffp, nonvolatile, rexxsyslib, utility, wb; the final set comes from
`rg` over `libs/` and `shared/`, task 1.2). The directory
`libs/include/ndk/` is added in `blitz_library` before the NDK
(`target_include_directories(... BEFORE ...)`, `cmake/BlitzLibrary.cmake:92`).
blitz2 and TED do not use `blitz_library`, so they are unaffected.

The shadow files are text of a fixed shape plus per-header lines taken
from the list of D4, so CMake writes them (`file(CONFIGURE)`/`file(WRITE)`)
at configure time into the build directory, the include directory pointing
there; the committed source is the list and the macro texts. A C tool in
`tools/` is added only if task 1.1 shows that CMake cannot read the NDK
headers reliably (D4); the expectation is that it can.

### D2 Varargs wrappers become `static inline`
The shadow header wraps the include:

```c
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wattributes"
#pragma push_macro("__stdargs")
#undef __stdargs
#define __stdargs inline __attribute__((__stkparm__))
#include_next <inline/intuition.h>
#pragma pop_macro("__stdargs")
#pragma GCC diagnostic pop
```

This is the prototype `shadow/inline/intuition.h` (the coordinator's
session scratch, temporary; the text above is the content). The
measurement is in the proposal. `__stdargs` appears in the inline headers
only in these wrappers (`AMIGA_VA_WRAPPER_ATTR`, noinline), so the
redefinition affects nothing else; `-Wattributes` is silenced only around
this include. About 11 KB saved over 49 libraries: an intended change of
those library files, no change of behaviour. It is its own commit, with
the changed files in `PREV_INTENDED`.

### D3 Safe macros and poison
After the `#include_next`, for a function with a safe form the macro of
the same name is redefined with the a3 (a4) value in a register gcc
chooses and exchanged around the call:

```c
ULONG __p____args = (ULONG)(___args);
__asm volatile("exg %4,a3\n\tjsr a6@(-588:W)\n\texg %4,a3\n"
    : "=d"(__v_ret), "+a"(__v0), ..., "+r"(__p____args)
    : "a"(__p__in_base) : "fp0", "fp1", "cc", "memory", "d1");
```

Measured in the audit for `rimisclib.c:769`: `move.l _ez+20,d2 / exg
d2,a3 / jsr a6@(-588:W) / exg d2,a3`. a3 is back; the OS keeps d2-d7 and
a2-a6. Cost: 4 bytes per call and register, one more callee-saved register
in the routine's `movem`, no stack use (so no trouble with sp-relative
operands, unlike `movem.l a3/a4,-(sp)`), condition codes untouched. For
a3 plus a4 (`AddAppIconA`) two operands and `exg %x,a3 / exg %y,a4`. Safe
forms are written for what the libraries use: `GT_SetGadgetAttrsA`,
`GT_GetGadgetAttrsA`, `EasyRequestArgs`, `AddAppIconA`, `AutoRequest`,
`TextFit`, `ChangeExtSpriteA`.

For every other affected function, and the varargs names `__X_va` that
reach them, the shadow does

```c
#undef BuildSysRequest
#undef __BuildSysRequest_base
#pragma GCC poison BuildSysRequest __BuildSysRequest_base ...
```

Measured in the audit: a call fails with `error: attempt to use poisoned
'AutoRequest'` and a note pointing at the shadow header (which can carry
the explanation as a comment); a library that uses none compiles to
identical assembler (windowslib compared). The compiler does the check in
the compile step of the object, as CLAUDE.md asks ("whatever the compiler
can do itself").

The affected functions (audit section 1): bsdsocket (WaitSelect,
getaddrinfo, gethostbyaddr_r, gethostbyname_r), datatypes (DoDTMethodA,
PrintDTObjectA, RefreshDTObjectA, SetDTAttrsA, SaveDTObjectA a3+a4), exec
(AddTask, RawDoFmt), gadtools (GT_SetGadgetAttrsA, GT_GetGadgetAttrsA),
graphics (ChangeExtSpriteA, FindColor, TextFit), icon (DrawIconStateA,
GetIconRectangleA a3+a4), intuition (AutoRequest, BuildSysRequest,
EasyRequestArgs, BuildEasyRequestArgs, SetGadgetAttrsA, DoGadgetMethodA),
layers (CreateUpfrontHookLayer, CreateBehindHookLayer), layout
(LayoutLimits, RefreshPageGadget, SetPageGadgetAttrsA a3+a4), locale
(FormatDate, FormatString, ParseDate), virtual (RefreshVirtualGadget,
RethinkVirtualSize), wb (AddAppIconA a3+a4). `FreeGadgets` is not on the
list (a0 only). The a5 functions (Supervisor, the layer lock calls) are
`native`: the NDK protects them.

### D4 The list and the configure check
A list file beside the shadow sources holds, per function: header, name,
registers, and the state `safe`, `poisoned` or `native`. A CMake script
(about 40 lines, run at configure next to `cmake/check-saveds.cmake`)
reads the toolchain's `inline/*.h`, collects the macros whose register
variables are `__asm("a3"|"a4"|"a5")` (what the audit's scans did per
macro), and compares the set with the list in both directions. The
generator of D1 reads the same list. The alternative, a C tool that
generates the safe macros from the NDK headers, is more robust but needs a
header parser and its tests (audit: 1-2 days against a few hours); it is
not chosen now and is reconsidered if the CMake scan turns out fragile.

A function whose safe form is not yet written has the transitional state
`pending`, which neither poisons nor protects; it exists only between the
commits of D6 and the list must hold no `pending` at the end (the check
rejects it in the last commit by a test of the final state, task 5.3).

### D5 Tests (every check has broken input)
- Configure check: a script test runs the comparison against a list
  without one name and expects the error text, in the style of
  `toolchain_saveds_broken` (`CMakeLists.txt:132-135`).
- Poison: a test compiles a source with a call of a poisoned function with
  the library flags and the shadow path and expects the compile error
  naming it.
- Safe macros: the library tests already record a3/a4 per routine
  (`libs/tests/rwe/rimisclib.c:316`, `riapplib.c:259-262`); the fix
  commits turn the entries into `[orig]` / `[fixed #N]` pairs.
- Inline wrappers: a check that a library including `proto/intuition.h`
  holds no `__EasyRequest_va` symbol (in the build step that checks the
  library, or a script test over the object).

### D6 Order of the commits
1. List, generator, shadow headers with the varargs wrappers (D2) only,
   the include path. `PREV_INTENDED` names the libraries that get smaller.
2. The configure check and its test (D4, D5), the list with every
   function `pending` except those of 3.
3. Safe macros and poison for the functions that change no behaviour:
   `AutoRequest` (rundebuglib), `TextFit` (rilvcallhooklib: the thunk's
   `/a3` goes), `ChangeExtSpriteA` (riwbspritelib: replaces its own
   `__asm`; kind-F deviation entry for #1028), and the poison of every
   function the libraries do not use. One rework commit, bytes only,
   named for the prev comparison; the poison test.
4. Each fix with its safe macro: #516 (`AddAppIconA`; replaces the
   `__asm` block at `riapplib.c:601-607`), #1027 (`EasyRequestArgs`, see
   Open Questions); the gtlib functions (#328, below). The state of the
   function goes from `pending` to `safe` in that commit.
5. Docs: `docs/libs/cmdlibs-port.md` (the rule now points at the build
   check; the hand-written `__asm` rule stays), `tests/README.md`,
   `TODO.md`.

#328: round RP fixed gtlib by its own means (`KEEP_A3`). The safe macro of
`GT_SetGadgetAttrsA`/`GT_GetGadgetAttrsA` would give one mechanism for all
libraries; the cost is 4 bytes per call and one callee-saved register,
which task 1.4 measures. Since these two names must be `safe` or
`poisoned` in the end, and gtlib uses them, they become `safe`; whether
`KEEP_A3` is then removed or kept is decided with the measurement.

## Risks / Trade-offs

- **A gcc update changes the register allocation** of the `"+r"` operand:
  a toolchain update is an intended change checked by the tests; the
  library tests record a3/a4.
- **The NDK changes the macro shape:** the shadow is text over the NDK's
  `#define`s; the configure check catches a new function, not a changed
  shape. A shadow that no longer fits fails to compile or warns, and a
  clean build has no warnings.
- **`exg` needs a free register** at the call; gcc picks one.
- **Poisoned names block identifiers of the same name** in a library
  (a local called `FindColor`): the compile fails and the name is renamed.
- **The thunk's `/a3` removal** in rilvcallhooklib is valid only with the
  safe macro; its library test checks it.

## Migration Plan

The commits in the order of D6; every one leaves `ctest --preset host` and
`ctest --preset all` green against a prev build, the changed library files
named in `PREV_INTENDED`. Issues #516 and #1027 get their usual steps
(label, website entry, close after the push) from the coordinator.

## Open Questions

1. **#1027 function form.** Does `EZRequest` in a string expression need
   more than a3 restored, that is, must it give back the space of its
   string arguments (the rule of the #846 comment, a3 = the first string
   argument)? Measure the function form first; then "restore a3" or "give
   back the space" (audit, note for the fix).
2. **gtlib and `KEEP_A3`.** Decided (user, 2026-11-14): switch to the safe
   macro as a rework and drop `KEEP_A3` (one mechanism), unless the macro
   turns out measurably larger.
3. **Generation by CMake.** Confirm in task 1.1 that `file(STRINGS)` and
   regular expressions read the NDK's register macros reliably; if not,
   a C tool in `tools/` (D4 alternative).
4. **No `-fbaserel` in libraries.** Confirmed (coordinator, 2026-11-14):
   no library is built with it, only blitz2 and TED. The libraries get the plain a4 form
   of wb.h, icon.h, layout.h and datatypes.h; confirm (task 1.3) that no
   library is built with `-fbaserel`, else the shadow's a4 macros clash
   with the NDK's `__baserel__` branch.
5. **Transitional `pending` state** (D4): decided (user, 2026-11-14): keep
   `pending` so each commit stays one topic; a test of the final list
   refuses any `pending` entry.
