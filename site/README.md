# bb2-c website

Source of the project website, <https://fubar-coder.github.io/bb2-c/>. It is
a [Hugo](https://gohugo.io/) site (extended edition) with the
[Hextra](https://imfing.github.io/hextra/) theme as a Hugo module. It is not
part of the CMake build; GitHub Actions builds and publishes it
(`.github/workflows/pages.yml`) on every push to `main` that touches `site/`.

The steps to build the site, the API reference and the command reference,
and how the Pages workflow does it, are also on the site itself:
<https://fubar-coder.github.io/bb2-c/docs/project-structure/build-docs/>.

The site is written for readers of the project, not for browsing the
repository. `docs/` stays the internal developer documentation and is the
source of facts, but is not included here; the pages are new texts.

## Local preview

```
podman run --rm -p 1313:1313 -v $PWD/site:/src docker.io/hugomods/hugo:exts-0.154.5 \
    hugo server --bind 0.0.0.0 --poll 700ms --enableGitInfo=false
```

`--enableGitInfo=false` is needed because only `site/` is mounted and the
container then sees no repository (the CI build has one). To keep the
"last modified" dates in the preview, mount the repository root and add
`--source site`. Add `:Z` to the volume on SELinux hosts.

A one-off build, as CI does it, into `site/public/`:

```
podman run --rm -v $PWD/site:/src docker.io/hugomods/hugo:exts-0.154.5 \
    hugo --gc --minify --enableGitInfo=false --baseURL https://fubar-coder.github.io/bb2-c/
```

The build must finish without errors or warnings.

## Theme

Hextra is pinned in `go.mod` and `go.sum`. CI never updates it. To move to a
newer release, run `hugo mod get github.com/imfing/hextra@vX.Y.Z` and
`hugo mod tidy` in `site/` and commit the result as its own commit.

## The command reference

The pages under `content/docs/libraries/commands/`, `amigaos/` and
`userlibs/` are generated by Hugo itself: the content adapter
`content/docs/libraries/_content.gotmpl` makes one page per library from
the command tables in `data/libraries/GROUP/NAME.json`, with the
Markdown of the partials in `layouts/_partials/cmdref/`; the shortcode
`library-list` lists the libraries of a section. Only the sections'
`_index.md` files are written by hand.

The JSON files are generated from the built library files by the host
tool `tools/cmdref` and committed. The CMake build checks in the build
step of every library that the committed file equals the generated one,
so a change of a library's declarations fails the build until the files
are updated: build the target `cmdref_update`, which copies the generated
files here, and commit them with the change. Do not edit them by hand.

A hand-written description and introduction of a library go into
`data/libintros/GROUP/NAME.yaml` (GROUP `acidlibs`, `deflibs` or
`userlibs`; for an AmigaOS library NAME is the deflibs library that opens
it, as `doslib`):

```
description: One sentence, for the library lists and search.
intro: |
  Markdown, shown above the commands.
```

Without the file, the page has a generated description and no
introduction.

A hand-written description of single commands goes into
`data/cmddesc/GROUP/NAME.yaml` (GROUP `acidlibs` or `userlibs`, NAME the
library), keyed by the command's name as the library declares it
(quote names with `$`):

```
"Left$":
  text: The first `Length` characters of `String$`.
  notes: |
    Markdown, shown after the command's forms (optional).
```

`text` (one or two sentences) is shown under the command's heading,
`notes` after its forms. A command without an entry shows only what the
library declares. Every statement must be checked against the library's
source or a test; a kept bug of the original names its issue as a link
(`([#285](https://github.com/fubar-coder/bb2-c/issues/285))`). The
content adapter `content/docs/libraries/_content.gotmpl` merges both files
into the pages.

In both files, a plain (unquoted) value must not contain `": "`: YAML
reads it as a new key and the build fails ("mapping value is not
allowed"). Quote such a value, or write it as a block scalar (`|` or
`>`), as `intro` and `notes` above.

## API reference

`static/api/` holds the Doxygen HTML of the library headers and sources
and of `shared/` when the Pages workflow builds the site: a job runs
Doxygen 1.16.1 in its official image with the repository's `Doxyfile`
(warnings are errors) before Hugo, and Hugo copies the
tree as it is to `/bb2-c/api/`. It is not committed (`.gitignore`). To
build it locally, from the repository root:

```
mkdir -p site/static/api
podman run --rm -v $PWD:/src -w /src ghcr.io/doxygen/doxygen:Release_1_16_1 Doxyfile
```

## Writing pages

* One directory per chapter in `content/docs/`, each with an `_index.md`; the
  order in the sidebar comes from `weight` in the front matter.
* Texts are plain English, explain instead of listing, and give examples
  instead of line numbers. No repository file names in page texts.
* The original documentation (the Blitz Basic 2 manual, Acid's and Red
  When Excited's library guides) is GPL and may be used: only where it is
  correct for the port, corrected or reworded where a clearer or correct
  wording exists, with the source named on the page.
* Internal links: always `{{< relref "/docs/chapter/page" >}}` in a link
  target (`[text]({{< relref "/docs/libraries" >}})`), also for a sibling page
  and with an anchor (`"/docs/chapter/page#heading"`). A relative link
  (`[text](page)`) is left as it is and resolves against the URL of the page
  it is on: on a page `/docs/chapter/page/` it points below that page and
  breaks. `relref` also fails the build when the target does not exist.
  Only the `link` of a `card` in a chapter's `_index.md` may be the plain
  name of a page of that chapter, since the chapter's URL is its directory.
* External links: always the full URL, including the menu entries in
  `hugo.yaml`. The site lives under the `/bb2-c/` subpath, and Hugo prefixes
  it to menu URLs that begin with `/`.
* The navbar search needs the menu entry with `params.type: search` in
  `hugo.yaml`; do not remove it.
* Notes and warnings use Hextra callouts:

  ```
  {{< callout type="warning" >}}
  Text of the warning.
  {{< /callout >}}
  ```

  Types are `info`, `warning`, `error` and `important`.
* Raw HTML in Markdown is switched off; use shortcodes.
